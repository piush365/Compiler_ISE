# Custom Arithmetic Expression Compiler Front-End: In-Depth Explanation

This document provides a comprehensive, in-depth explanation of the Custom Arithmetic Expression Compiler Front-End. It is designed to give you complete clarity on the codebase, concepts, methodology, and execution phases, preparing you thoroughly for your viva presentation.

## 1. Project Overview

This project implements the first two phases of a compiler (the **Front-End**) for a custom arithmetic expression language. These phases are **Lexical Analysis** and **Syntax Analysis**. 
It is written in pure Python and does not include later compiler stages like semantic analysis, intermediate code generation, optimization, or target code generation.

The compiler takes raw source code (arithmetic expressions) as input and processes it to determine if it is syntactically valid according to defined rules (a grammar). If it's valid, it can build an Abstract Syntax Tree (AST); if invalid, it utilizes an AI-powered module to explain the syntax error to the user.

## 2. Input and Expected Output

### What to Input
The input is a string of source code representing assignments and arithmetic expressions.
**Examples of valid input:**
- `x = 5.5 + -3 * sin(y);`
- `z = x ^ 2 ^ 3;`
- `result = (10 % 3) / log(x); y = -x;`

### Expected Output
The output depends on the parser being used and whether the input is valid.
1.  **Lexer Output:** A sequence of Tokens (e.g., `IDENTIFIER('x')`, `ASSIGN('=')`, `FLOAT('5.5')`, ...).
2.  **Parser Output (Valid Input):**
    *   **LL(1) Recursive Descent Parser:** Prints an Abstract Syntax Tree (AST), which is a hierarchical data structure representing the parsed code.
    *   **SLR(1) Bottom-Up Parser:** Prints a step-by-step trace of the parsing stack, input buffer, and the Shift/Reduce actions taken, culminating in an `Accept!` state.
3.  **Parser Output (Invalid Input):**
    *   A raw syntax error pointing out the exact line, column, unexpected token, and the expected tokens.
    *   **AI Explanation:** A human-readable, beginner-friendly explanation generated by an AI model (Groq/Gemini) explaining the error and suggesting a fix.


## 4. Compiler Phases and Methodology

The compiler is divided into distinct, hand-written modules. Let's explore each phase in depth.

### Phase 1: Lexical Analysis (`lexer.py`)

**What it does:** Lexical analysis (Scanning) is the very first phase. It reads the raw input source code character by character and groups them into meaningful sequences called **Tokens**. It strips out whitespace and comments.

**Methodology / Concept:**
- It uses **Regular Expressions (Regex)** to define patterns for each token type.
- Example token patterns:
  - `INT`: `\d+`
  - `FLOAT`: `\d+\.\d+`
  - `IDENTIFIER`: `[a-zA-Z_]\w*`
  - `PLUS`: `\+`
- The `Lexer` class matches these regex patterns against the input string.
- When a match is found, it creates a `Token` object containing the `type` (e.g., `IDENTIFIER`), the actual `value` (e.g., `'x'`), and tracks the exact `line` and `column` number. Tracking position is crucial for reporting accurate errors later.

### Phase 2: Syntax Analysis (Parsing)

Syntax analysis verifies that the sequence of tokens conforms to the structural rules of the language. These rules are defined by a **Context-Free Grammar (CFG)**.

The project defines the grammar and implements **two different types of parsers** to demonstrate different parsing methodologies.

#### The Grammar (`grammar.py`)
- **Original CFG:** Defines standard math rules, enforcing operator precedence (e.g., `*` before `+`), associativity (left-associative for `+`, `-`, `*`, `/`, but right-associative for power `^`), and unary operators.
- **FIRST and FOLLOW Sets:** The script algorithmically computes the `FIRST` sets (what terminal tokens can appear first in a given rule) and `FOLLOW` sets (what terminal tokens can immediately follow a non-terminal). These mathematical sets are foundational for both predictive top-down parsing and bottom-up parsing.
- **Grammar Transformation:** Top-down parsers get stuck in infinite loops with "Left-Recursive" grammars (e.g., `Expr -> Expr + Term`). Therefore, `grammar.py` also provides a mathematically transformed version of the CFG where left-recursion is eliminated and common prefixes are left-factored.

#### Parser A: LL(1) Predictive Recursive Descent (`parser_recursive_descent.py`)
**Methodology (Top-Down Parsing):**
- It starts at the top (the `Program` rule) and works its way down to the tokens (leaves).
- **"Recursive Descent"**: Every non-terminal in the grammar (like `Stmt`, `Expr`, `Term`) has a corresponding Python function (`parse_stmt()`, `parse_expr()`). These functions call each other recursively based on the grammar rules.
- **"LL(1)"**: It reads from **L**eft to right, constructs a **L**eftmost derivation, and uses **1** lookahead token.
- **"Predictive"**: Because the grammar is left-factored, the parser looks at the current token and uses the `FIRST` sets to definitively predict which grammar rule to take without needing to backtrack.
- **Abstract Syntax Tree (AST)**: As the functions successfully parse segments of the code, they instantiate Python data classes (`BinOp`, `UnaryOp`, `Num`, `Var`) and link them together to build an AST, a tree representation of the code's logical structure.

#### Parser B: SLR(1) Bottom-Up Parser (`parser_bottom_up.py`)
**Methodology (Bottom-Up Shift-Reduce Parsing):**
- Instead of starting at the root, it starts at the leaves (the tokens) and tries to group them backwards (reduce) up to the root (`Program` rule).
- It uses the original, unmodified left-recursive grammar.
- **State Machine Construction**: The code calculates LR(0) items, computes closures and goto transitions, to dynamically build a finite state machine representing all possible parsing states.
- **Parsing Table**: It builds an ACTION table (Shift, Reduce, Accept, Error) and a GOTO table using the state machine and the `FOLLOW` sets to resolve conflicts (Simple LR or SLR logic).
- **Stack-based Execution**: The parser maintains a stack of states and symbols. It looks at the top of the stack and the incoming token, consults the ACTION table, and either **Shifts** (pushes the token to the stack) or **Reduces** (pops a recognized rule off the stack and pushes the resulting non-terminal). It prints this stack trace live.

### Phase 3: The AI Error Explainer (`ai_error_explainer.py`)

**What it is:** An integration with Large Language Models (Groq API primarily, with Google Gemini as a fallback) to provide intelligent syntax error explanations.

**How it works (The Architecture Constraint):**
It is critical to understand that the **AI does NOT parse or compile the code**. It is strictly a translation layer. 
1. When the hand-written parser (`parser_recursive_descent.py` or `parser_bottom_up.py`) encounters an unexpected token, it halts and triggers a `SyntaxErrorExt`.
2. The parser bundles the error context into a `SyntaxErrorInfo` object. This includes the offending token, the exact line/col snippet, and mathematically derived **Expected Tokens** (pulled directly from the CFG `FIRST/FOLLOW` sets).
3. The `ai_error_explainer.py` script takes this structured, rigid data and wraps it in a prompt.
4. The LLM translates this rigid compiler state into a beginner-friendly, plain English explanation and suggests a 1-line fix.

**Why this design?**
Relying on an LLM to parse code is unpredictable and slow. By keeping the parser deterministic (hand-written Python) and only invoking the LLM when an error occurs to translate the error state, the compiler remains fast, exact, and robust while still offering a next-generation user experience for debugging.

## 5. Summary for Viva Presentation

If you are asked to summarize the project quickly, hit these main points:
1.  **Scope:** It's a front-end compiler (Lexer + Parser) for mathematical expressions, built in pure Python.
2.  **Lexer:** Uses regex to tokenize the input and tracks exact positioning.
3.  **Grammar Theory:** Demonstrates theoretical computer science by calculating FIRST/FOLLOW sets and handling both left-recursive and non-left-recursive CFGs.
4.  **Parsers:** Implements *both* a Top-Down LL(1) Recursive Descent parser (which builds an AST) and a Bottom-Up SLR(1) Shift-Reduce parser (which uses a stack/state-machine trace).
5.  **AI Integration:** Innovates error handling by piping deterministic parser error states into an LLM (Groq/Gemini) to generate human-readable explanations, strictly acting as a translation layer without compromising the compiler's integrity.
